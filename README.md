# QIMP

Android 端**纯本地**音乐播放器：Rust 负责全部逻辑（扫描 / 元数据 / 索引 / 歌词），Flutter 只负责界面。（本项目完全由d老师生成）

## 目录结构

| 路径 | 说明 |
| --- | --- |
| `rust/core/` | 核心库，纯 Rust、不依赖 Android，可在宿主机直接 `cargo test` |
| `rust/audio/` | 播放层：symphonia 解码 + 播放队列 + 播放引擎；输出设备用 trait 抽象（Android 走 Oboe） |
| `rust/ffi/` | FFI 边界层，绑定由 flutter_rust_bridge 生成 |
| `app/` | Flutter 应用（Android 平台） |
| `scripts/build-apk.sh` | 一键构建 APK：先编 Rust 成 `.so`，再交给 `flutter build apk` |

## 权限说明（重要）

- **Android 11+ 必须授予“所有文件访问”**（`MANAGE_EXTERNAL_STORAGE`）。原因：核心扫描器基于
  `std::fs` + `walkdir`，需要真实文件路径；SAF 给的 `content://` URI 无法用它遍历。
  首次启动会引导你跳到系统设置页；调试时也可用 adb 直接授予：

  ```bash
  adb shell appops set --uid com.qprs.musicplayer MANAGE_EXTERNAL_STORAGE allow
  ```

- 扫描范围是下面这些目录中**实际存在**的那些（由 Rust 侧 `suggest_scan_roots()` 返回）：
  `/storage/emulated/0/{Music,Download,Podcasts,Recordings,Documents}`。
  扫描只负责**建索引**（解析标签、写进 SQLite），**不会**自动把歌塞进曲库；
  收哪些歌由用户在主页上挑（＋ 添加歌曲），不想要的可以「从库中删除」或「从储存中删除」。
- 索引数据库落在应用私有目录：`files/library.db`（SQLite + WAL），不需要任何权限。

### 播放列表的导入 / 导出

**导入**（抽屉右上角的 ⤓）：用系统文件对话框挑一份 `.m3u` / `.m3u8` / `.xspf`，
Rust 侧解析、建一个新列表、把条目按文件里的顺序填进去。

- 认的格式：`.m3u` / `.m3u8`（注释、`#EXTINF`、CRLF、带不带 `#EXTM3U` 头都行）、
  `.xspf`（取 `<trackList>` 里的 `<location>`，列表名取 `<trackList>` **之前**那个 `<title>`）；
  扩展名不认识时按内容嗅探（SAF 有时给不出像样的文件名）。
- 条目写法都做了归一：`file://` 前缀、百分号编码（`%E5%A4%9C…`）、引号、相对路径、
  Windows 反斜杠。网络地址（`http://` 等）跳过并计数——本地播放器放不了它们。
- 文件名与文本编码按「BOM → UTF-8 → GB18030」解，与 `.lrc` 用的是同一个函数
  （`metadata::decode_text`）：中文圈导出的列表常是 GBK。
- 条目对到曲目上是三级匹配（`playlist_file::PathIndex`）：**完整路径 → 归一后相同
  （大小写 / `\` 与 `/`）→ 文件名唯一命中**。撞名（两个目录里有同名文件）时**不猜**，算对不上。
- 对不上的条目只是**跳过并计数**，不会替用户往索引里塞记录：没扫到过是「扫描」该干的事。
  一条都没对上时会明说「先在主页扫描一次」——列表建出来是空的，不说原因只会让人以为功能坏了。

**导出**（每一行的 ⋮ → 导出）：选 M3U8 还是 XSPF，再用系统对话框挑保存位置。
文本由 Rust 生成（`playlist_file::export_m3u8` / `export_xspf`），落盘在 Kotlin 侧
（`content://` 只有它能写）。xspf 里的路径写成 `file://` + 百分号编码再做 XML 转义。

> 为什么还要绕系统对话框：Android 上用户挑的文件可能在别的应用或 SD 卡上，
> 系统只给一个 `content://`，core 的 `std::fs` 用不了它。所以 Kotlin 侧只负责搬字节
> （`MainActivity` 的 `com.qprs.musicplayer/files` 通道，上限 4 MB），
> 解析与生成全在 Rust —— 于是这些规则能在宿主机上直接测，不必真机试一遍。

### 歌词

播放界面上面那块在**手机上竖着**是**两页**：封面页与歌词页。翻页靠封面**左上角**那颗
「歌词」按钮，回封面靠歌词页**左上角**那颗专辑图标。
歌词页顶上原来那一行是「[歌词图标] 歌词 …… [回封面]」：用户说左边那两个字和图标是废话
（整页都是歌词，不用再标一遍），而且「回封面」靠右摆、横屏时正好贴着两列的交界，
所以标签删掉、按钮搬到了左上角（见 `lyrics_view.dart` 的 `_header`）。
窗口够宽时（平板、手机横屏）根本没有「翻页」这回事——两样东西并排成左右两栏，
见「大屏 / 横屏的播放界面」。

翻页**没有滑动手势**（用户明确要求关掉：「滑动进歌词」和「左滑下一曲」太容易撞，
起点偏一点、甩快一点，意思就变了）。滑动只剩这些：

| 区域 | 右滑 | 左滑 | 上下滑 |
| --- | --- | --- | --- |
| **封面那张图上** | 上一曲 | 下一曲 | 音量 ±（跟手线性） |
| 封面之外的空白 | — | — | — |
| 歌词页（右下那块） | 回封面页 | —（不切歌） | 滚动歌词 |

手势区域**就是封面那张图本身**（内层手势识别器），它周围的空白什么都不接：
之前整块区域都响应，范围大得离谱——上下滑想调音量、手指却落到图外面，
或者想轻轻划一下封面却换了歌（用户反馈过两次，第二次就是「范围有点大」）。

歌词页的滑动**不切歌**：要换歌请用下面那排按钮（它们在两页上都看得见）。

词源（`core::metadata::read_lyrics`）：

1. **同目录同名的 `.lrc`**（`歌.mp3` → `歌.lrc`，扩展名大小写不敏感，手机上常见的 `歌.LRC` 也认）；
2. 否则看**文件内嵌歌词**：ID3v2 的 `USLT`（lofty 的键是 `ItemKey::UnsyncLyrics`
   ——`ItemKey::Lyrics` 在 ID3v2 里对应的是带时间戳的 `SYLT`，lofty 不支持）、
   Vorbis 的 `LYRICS` / `UNSYNCEDLYRICS`、MP4 的 `©lyr`。两个键都在时**优先带时间轴的那份**。

**时间戳相同的几句算同一条**（`[00:10.00]原文` + `[00:10.00]translation` 就是双语歌词）：
core 里合成一条、文本用 `\n` 连接，界面按一条高亮与滚动，那一条占两格高度。

`.lrc` 的编码按「BOM → UTF-8 → GB18030」猜：中文圈下载的 `.lrc` 大量是 GBK/GB18030，
直接当 UTF-8 读会整片 `���`（这就是引入 `encoding_rs` 的唯一原因）。
内嵌歌词经常是**没有时间戳的整段文字**，那种照样显示，只是不做高亮与自动滚动
（`Lyrics::synced == false`）。

### 编辑主题（背景颜色）

入口在**主页右上角**那颗调色板（`ThemeButton`，三块主视图共用同一条顶栏，所以换到
「我的音乐」「队列」也还在——用户找它的时候不该扑空）；点开是 `theme_page.dart`。

- **改一下立刻生效、立刻落盘**，没有「保存」按钮：照桌面小部件那个设置页的做法
  （那边也是改完立刻重画），用户不用盯着屏幕猜「保存了没有」。
- **这一页本身就是预览**：页面自己也长在新底色上。不像小部件那边还得另设一个预览框
  ——照着真界面再画一遍的预览，早晚会和真的长不一样。
- **颜色 = 预设 + 红/绿/蓝滑块**（`kBackgroundPresets`）：只有预设会觉得被限制，
  只有滑块则调个纯白要滑三下。滑块 255 档 = 一档一个整数。
- **拖动中只改界面，松手才写文件**（`ThemeSettings.setBackground(save: false)` →
  `onChangeEnd` 再写一次）：一次拖动几十个事件，没必要写几十遍文件。
  判断「要不要写」用的是「已经写进去的那一份」（`_saved`），不是「当前值变了没有」
  ——松手那一下的值和拖动中最后那一下恰好相同，只看变化会漏掉这次写。
- 存成应用私有目录下的一小份 JSON（`theme.json`，跟 `library.db` 放一起）：
  只存一个颜色，为它引一个 `shared_preferences` 不划算。读不出来就当没设过（用出厂主题）、
  写不进去也只是「这次改的没记住」——两种都不值得弹个用户看不懂的错。
- 主题在**跑第一帧之前**读回来（`main.dart` 里 `await theme.load()`）：
  晚一步就会先闪一下出厂配色，再跳成用户选的底色。

配色不是只刷一层底：`backgroundScheme()`（纯函数，`flutter test` 直接测）整族一起推。

- 只改 `scaffoldBackgroundColor` 是不行的：M3 里顶栏、卡片、弹窗、抽屉、底部条用的都是
  `surface*` 那一族颜色，它们仍来自种子的**中性色**。只把页面底刷成深蓝，上面就会浮出
  一块块米白，而正文（`onSurface`）还是黑的——等于半个界面瞎了。
- 文字反过来按明暗给：亮底深字、暗底浅字（判据是 **HSL 明度**，不是 `computeLuminance()`
  ——后者对中灰只有 0.22，会掉进「暗底」那一侧，而中灰上其实黑字更清楚）。
  测试里按 WCAG 的对比度卡（正文、次要文字都要 > 4.5:1）。
- 层叠色在底色上挪几个色阶（对齐 M3 的排法：亮底往下压、暗底往上提），
  弹窗 / 卡片 / 菜单才浮得起来；`brightness` 也跟着切，组件里那些硬编码的深浅才对得上。
- 提示条（SnackBar）走反色：深底上弹一条浅的，不然看着像缺了一块。
- **强调色（那支青）不动**：改背景不该顺手把按钮、进度条一起换掉。
  已知边界：挑一个和青色太像的底色时，按钮会有点融进背景——要一起调，
  那是下一步把强调色也做成可选的活。

### 大屏 / 横屏的播放界面

判定全在 `lib/src/tablet_layout.dart`，三个纯函数（`flutter test` 直接测），页面上只做选择：

| 判断 | 规则 | 为什么这么定 |
| --- | --- | --- |
| 是不是平板 | 窗口**最短边 ≥ 600** | 600 就是 Android 资源限定符里的 `sw600dp`——跟着系统走，用户眼里的「平板」和我们的判断才是同一批设备 |
| 横没横过来 | 宽 > 高 | 手机横过来之后竖向只剩三百来点 |
| 主页方向 | 手机上只给竖屏两个方向，平板随意 | 手机横着看曲库只是把列表压成中间一条，两边全空 |

用**最短边**而不是宽度判平板：竖着拿、横着拿是同一台机器，转个方向就换一套布局
只会让人以为界面坏了。

播放界面一共三套版式（`player_page.dart` 的 `_body`）：

| 窗口 | 版式 |
| --- | --- |
| **平板** | 左栏＝封面 + 控制区（标题 / 进度 / 两排按钮），右栏＝**整块歌词**。地方够宽，歌词就该一直看得见，所以翻页按钮都不出现（`LyricsView.onBack` 传 `null`：连那条顶栏都不画，一点位置也不占），歌词栏上的横向滑动也不接 |
| **手机横屏** | 左栏＝封面，右栏＝控制区。封面**左上角**那颗「歌词」把左栏换成歌词，右栏始终是控制区——看歌词时照样能暂停 / 切歌 / 拖进度；换回封面点左栏**左上角**那颗专辑图标 |
| **手机竖屏** | 老样子：封面页与歌词页二选一，进歌词页走封面左上角那颗按钮，回封面走歌词页左上角那颗 |

其它几条：

- **曲库主页在手机上锁竖屏**（`LibraryPage.didChangeDependencies` 里按 `homeOrientations`
  下发一次）：手机横过来看曲库只是把列表压成一条。**平板不锁**——11 寸横着拿是常态。
- 方向这件事**只管主页**：打开播放界面之前先把限制放开（`_openPlayer`），退出时再锁上——
  手机横屏播放正是靠这个才转得过去。
- 手势规则一字不改：切歌与音量**仍然只认封面那张图**（分栏时就是左栏里那张，
  提示气泡也还闪在那儿）。
- 三套版式共用同一份控制区（`_transport`）与同一个 `LyricsView`，
  所以按钮顺序、间距、歌词手感不会各长一样。

> 手上只有手机时怎么试平板那套：`adb shell wm size 1600x2560` + `adb shell wm density 320`
> 之后窗口就是 800×1280 逻辑像素（最短边 800），界面立刻按平板排；
> 试完记得 `adb shell wm size reset`、`adb shell wm density reset` 还原。
> 反过来，平板想试手机那套：把 size 调成 `1200x2600`（密度不变）就够了。

### 随机播放与循环模式

两个开关是**两个独立的维度**：随机决定「下一首是谁」，循环决定「一轮放完怎么办」。
一共六种组合，只有一种要特别说明——**随机 + 单曲循环**：

| 循环 ↓ / 随机 → | 关闭 | 开启 |
| --- | --- | --- |
| **关闭** | 放完最后一首就停 | 一轮放完就停 |
| **列表循环** | 放完回到第一首 | 一轮放完自动重开一轮（顺序重抽） |
| **单曲循环** | 同一首一直循环（手动「下一首」仍然换歌） | **同「列表循环 + 随机」**：一轮之内不重复地放完整个列表，再自动重开一轮 |

为什么不按「同一首无限循环」办：随机本来就没有「顺序」可言，把同一首无限循环，等于把
列表里别的歌**全锁在门外**——用户看到的是「随机也开着、循环也开着，却一直只有这一首」。
所以随机开着时让随机说话：一轮把列表放完（每首一次），放完就自动重开一轮。
要单独循环某一首，先把随机关掉——关掉随机不会改变当前这首，接着按顺序往下走。

规则全在 `rust/audio/src/queue.rs::PlayQueue::advance`（纯逻辑，宿主机可测）：

- 随机下 `auto`（自然播完）那一路**不再**走「留在原地」，而是照常抽下一首没放过的；
- 一轮抽干之后，只有循环为「关闭」才返回 `None`（停），列表循环 / 单曲循环都重开一轮。

界面上也对得上：随机开着时循环按钮的提示会多一句
「循环：单曲循环（随机下按列表循环走，点击切换）」（`playback_buttons.dart`）。

### 定时播放

底部那排按钮里的秒表：预设 15 / 30 / 45 / 60 / 90 分钟，**「自定义…」可以自己输入分钟数**
（1 ~ 1440，也就是最多一天；输入不合法时「开始」是灰的）。到点只暂停、不停止：
醒来点一下播放键就接着听，位置还在。

### 接着上次的听（整队）

「继续播放」存的是**整份队列**，不只是那一首——只还原一首的话，重启之后「下一曲」
就是个死键（用户就是这么报上来的）。

- 落库：`play_queue` 表（`position` / `track_id` / `is_current`，schema v3），
  队列或当前项一变就整表重写一次（`Db::save_queue`）；
  当前项用一列而不是配置项：那一行会跟着曲目一起被级联删掉，不会指向一条没了的记录。
- 读回：`Db::resume_queue()` 内连接 `track` 拿路径（已经从库里消失的条目直接不出现），
  并把「上次那一首」在新列表里重新定位；**进度从 `play_state` 现取**，
  不在这份快照里另存一份——那边每两秒刷新，是更新鲜的那份。
- 落地：`ProgressApi.plan()`（纯函数，宿主机可测）把文件已经不在了的条目剔掉，
  当前项跟着移到新位置；它正好也被删了就退回队首、进度清零。
  然后 `setPlayQueue(autoplay: false)` + `playerLoad(position)`：装好但不响。

> 未持久化：随机 / 循环模式。它们跟着**引擎的生命周期**走（进程重启即回到默认），
> 队列本身与「上次听到哪」才是用户可见的连续性。

### 通知栏 / 锁屏上的封面

那一片通知里的图有两条路要喂，缺一条就会出现「通知上有、媒体卡片上没有」这类怪相：

1. **通知自己**：`NotificationCompat.Builder.setLargeIcon(bitmap)`（收起时的缩略图）；
2. **MediaSession 的元数据**：`METADATA_KEY_ART`（Android 13+ 的媒体卡片、锁屏、车机读它）
   与 `METADATA_KEY_ALBUM_ART`（有些车机只认这个）。

三条实现上的讲究：

- **取图走 JNI，不经过 Dart**：`PlaybackBridge.coverBytes()` → `playback_bridge::cover_bytes()`
  → `metadata::read_cover`（内嵌图优先，其次同目录 `cover.jpg` / `folder.jpg`）。
  用户把 App 从任务列表划掉之后 Dart 早就不在了，但通知栏照样要显示封面。
- **异步 + 过期丢弃**：读文件 + 解码要几十毫秒，放在服务那条 500ms 的轮询里会卡住更新，
  所以交给 `artworkExecutor`；回来时如果 `cachedTrackId` 又变了就整份丢掉——
  不然会出现「放着 B、通知上是 A 的封面」。图到了之后重跑一次 `refresh()`，
  通知的签名里带了「有没有封面」，于是会重发一次。
- **缩到 512px**（`Artwork.kt`，尺寸计算是纯函数，`gradlew :app:testDebugUnitTest` 里测）：
  内嵌封面动辄 1400×1400，原图塞进 MediaSession 的元数据、系统每查一次走一次 Parcel，
  很容易撞上 `TransactionTooLargeException`，现象是**整条通知干脆不显示**。
  通知上那张图只有几十 dp，缩了看不出差别。

### 桌面小部件

四种尺寸，两种长相（`PlaybackWidget.kt`）：

| 尺寸 | 长相 | 内容 |
| --- | --- | --- |
| 2×1 / 4×1 | **一行式**（`widget_row.xml`） | 左封面，中间上歌名、下「上一曲 · 播放 · 下一曲」 |
| 2×2 / 4×2 | **卡片式**（`widget_card.xml`） | 上部封面，下面歌名，再下面「随机 · 上一曲 · 播放 · 下一曲 · 循环」 |

两份布局的右上角都浮着一颗**设置齿轮**（最外层包一层 `FrameLayout` 才「叠」得上去）。

四个尺寸是**四个 receiver**，不是同一个类注册四次：Android 认的是组件（包名 + 类名），
同一个类注册四次只会合成一个，系统里就只剩一档可选。布局只有两份——宽度交给
RemoteViews 自己撑开，2×1 与 4×1 没有任何区别。

几个关键决定：

- **长什么样看实际尺寸**，不看用户当初挑的是哪一档（`widgetShape()`，纯函数，
  `gradlew :app:testDebugUnitTest` 里测）：小部件是可以被拉大拉小的，
  2×1 拉成 2×2 就该长成卡片式。
- **数据与按钮都走 JNI**（`PlaybackBridge`），不经 Flutter：用户把 App 从任务列表划掉之后
  小部件照样得显示、照样得能按。按钮发到 `PlaybackService`，与通知栏那几个按钮
  **共用同一组 ACTION**，于是「按一下的效果」只有一份实现。
- **状态由服务推**：`updatePeriodMillis = 0`（系统最快也只能 30 分钟刷一次），
  服务每 500ms 轮询一次，签名一变（状态 / 曲目 / 封面 / 随机 / 循环）就重画所有小部件。
- **封面按曲目缓存**：刷新很频繁，而解图要几十毫秒；曲目没变就不重新读盘。
- **按钮颜色用滤镜，封面绝不用**：滤镜挂在**某个 view** 上，每个按钮各有各的 id，
  所以染按钮永远不会染到封面；封面是照片，被染色就是「滤镜脸」。
  随机 / 循环的开关状态改用**透明度**（关 45%、开 100%）区分，
  于是「两个状态 + 用户选的颜色」不再互相打架。

右上角那颗**齿轮**进的是 `WidgetSettingsActivity`（原生页面，不是 Flutter 里的一页）：

- 为什么是原生：用户点齿轮时 Flutter 引擎可能压根没起来（App 已被划掉），
  为改个颜色把整个引擎拉起来的代价不对等。
- **改完立刻生效**，没有「保存」按钮：每次改动都写进 `SharedPreferences`，
  然后重画预览 + `updatePlaybackWidgets()` 重画桌面上所有小部件。
- **实时预览**：把 `widget_card.xml` 那份布局**本尊** inflate 进预览框（不是照着再画一遍，
  照着画早晚会和真的长不一样），底色用一层深→浅的灰渐变，白色与黑色各能看到一半。
- **封面大小**：滑块给的是「占可用空间的比例」（100% = 七成），
  上限被可用空间夹死（`coverSizeDp()`，纯函数，单测覆盖）——小部件的尺寸是启动器给的，
  封面长过头会把下面那排按钮顶出边界，而 RemoteViews 溢出是**直接裁掉、不报错**。
  想让图变小用的是 `setViewPadding`：布局参数那一对（`setViewLayoutWidth/Height`）
  带 gravity、是 API 31 才有的，而 RemoteViews 的动作是在**启动器进程里用反射执行**的，
  老启动器上找不到这个方法。
- **颜色 = 预设 + R/G/B 滑块**：预设解决最常用的那几个色，滑块解决「我就要壁纸上那个色」；
  只有预设会觉得被限制，只有滑块则调个白色要滑三下。
- 设置是**全局一份**（不是每块小部件一套）：桌面上摆两块的人多半想要它们长得一样，
  按 id 存反而要解释「这块和那块为什么不一样」。

已知边界：进程被系统回收之后 Rust 引擎也没了，此时小部件退化成「QIMP」且按键无效
——和通知栏一样，播放器没在跑的时候确实没有东西可控制。

### 播放能放哪些格式

解码用 symphonia，**支持**：mp3 / flac / wav / aiff / m4a(mp4+aac+alac) / ogg(vorbis) / ogg(opus)。
其中 **Opus 不是 symphonia 自带的**（0.6 连特性都没有），靠 `symphonia-adapter-libopus` 把 libopus 接进来，
构建时会把 libopus 源码一起编进 `.so`，所以 Android 侧只需要 NDK 工具链、不依赖系统里的库。
这一点很值得记一笔：**手机录音与不少下载源的 `.ogg` 其实是 Opus**，只带 vorbis 时会直接“播不了”。

**不支持**：ape、wma、dsf/dff、mpc —— symphonia 没有这些解码器，扫得到但播不了，
播放失败时会在底部播放条上直接显示原因，不会静默失败。

**时长有两个来源**：曲库那份来自标签/容器解析（lofty），列表里显示的就是它；
解码器那边还会从容器里算出一份（`PlayerSnapshot.duration_ms`）。曲库那份是 0 时
（有些文件标签里就是没有时长，例如**把 mp4 改名成 `.mp3` 的“提取音频”**）UI 用解码器那份兜底，
播放时也会顺手把它补回曲库（`Db::fill_duration`，只补 0、不覆盖已有值）。

**被截断的文件**（下载没下完）按“这首放完了”处理：能播的部分照播，之后自动接下一首，
不会因为一个坏文件把队列卡住。跳转落点实测：真 mp3 差 -31~-68ms、真 flac 差 -18~-86ms
（精确跳转只能落在帧 / 包边界上，且只会偏早），UI 上的 400ms 容差就是按这个定的。

## 几个必须知道的坑

- **直接 `flutter build apk` 不会编译 Rust**。本项目用“手动 jniLibs”方案（没启用 flutter_rust_bridge 的
  cargokit 插件），所以请始终用 `scripts/build-apk.sh`；否则 APK 能装上、能启动，但一调 FFI 就崩。
  `app/android/app/src/main/jniLibs/` 是构建产物，已被 git 忽略，需要时就地重新生成。
- Flutter 默认打 `armeabi-v7a` / `arm64-v8a` / `x86_64` 三个 ABI，**三个都要有 `.so`**，脚本已覆盖。
- `flutter_rust_bridge` 版本在**三处必须一致**：`rust/ffi/Cargo.toml`、`app/pubspec.yaml`、codegen CLI。
- Gradle 发行包走腾讯镜像（见 `app/android/gradle/wrapper/gradle-wrapper.properties`）：
  `services.gradle.org` 在本机连接超时，`mirrors.cloud.tencent.com/gradle/` 正常。
- 首次 `flutter build apk` 会下载 Gradle 9.3.1 + AGP 9.1.0 + Kotlin 依赖（约数 GB、十余分钟），
  之后增量构建在秒级。
- **C++ 运行时必须自己链**（`rust/ffi/build.rs`）：Oboe 是 C++ 库，而 cargo 在 Android 上用 NDK 的
  `clang`（C 驱动）做最终链接，不会像 `clang++` 那样自动带上 libc++。少了这一步，`.so` 里会留下
  `__cxa_pure_virtual` 这类未解析符号，**编得过、装得上，一启动就 `dlopen failed`**。
  排查手法（改完链接参数后建议都跑一遍，确认符号已静态解析）：
  ```bash
  unzip -p app/build/app/outputs/flutter-apk/app-debug.apk lib/arm64-v8a/libmusicplayer_ffi.so > /tmp/x.so
  llvm-readelf --dyn-syms /tmp/x.so | awk '$7=="UND" {print $8}' | grep -E 'cxa|_Z'
  # 只剩 __cxa_atexit/__cxa_finalize（由 Android 的 libc.so 提供）才是正常的
  ```
- **`symphonia` 需要 rustc ≥ 1.85**：`rust/audio/Cargo.toml` 单独抬高了这个 crate 的 `rust-version`，
  `core` / `ffi` 仍保持 workspace 的 1.82，别在 workspace 层面统一抬高。
- **Oboe 的立体声回调帧类型是 `(f32, f32)`**（帧切片，不是扁平采样），
  且回调里不能分配内存——所以交错缓冲要预先分配、越界部分补静音。
- 真机验证播放是否真的在出声（不用听）：
  ```bash
  adb shell dumpsys media.audio_flinger | grep -E 'qprs.*actual_seconds'
  # 隔 20 秒再跑一次，actual_seconds 的增量应约等于 20 秒
  ```
- **widget 测试的默认窗口是 800×600 逻辑像素**——最短边正好 600，会被判成**平板**
  （见上面「平板上的播放界面」）。所以 `player_page_test.dart` 在 `setUp` 里统一把窗口
  换成 1080×2400 @3x（真机上就是 360×800）：测手机的用例才真的跑在手机那一套上；
  平板的用例自己再换成 1600×2560 @2x（最短边 800）。写新的尺寸相关用例时别忘了这条。
- **进度条的 `value` 必须落在 `[0, max]` 里**，否则 Flutter 直接断言失败、整屏红字
  （真机上遇到的：时长未知时 `max` 给 1、`value` 却是 20038ms 的播放位置）。
  所以 `SeekSlider` 里 `max` 与 `value` 共用同一个上界；时长两份都不知道时统一画成空的、
  并且不给拖。
